# Non-negotiable principles — otel-signoz

The real value of this plugin isn't "having OpenTelemetry." It's the pair:
**a Trace ID always present on an error response** + **a Trace ID shown to the user only on a genuine
system failure**, with the same trace crossing frontend → API → Auth → SQL/queues.

These principles apply **regardless of language or framework**. `references/dotnet-backend.md` and
`references/angular-frontend.md` are this plugin's one deeply validated, tested reference
implementation; `references/other-stacks.md` covers the same principles for anything else.

## 1. Service identity (resource attributes)

| Attribute | Value | Rule |
|---|---|---|
| `service.name` | `<base>-api`, `<base>-auth`, `<base>-ui`, `<base>-worker-<x>`, `<base>-func-<x>`, `<base>-svc-<x>` | **Identical across every environment.** Never concatenate the environment (`-dev`, `-hml`). |
| `service.namespace` | `<base>` | Groups every service of the same system. |
| `service.version` | `vYYYYMMDD.HHMM`, or the target project's own release scheme, generated by CI/CD | Lets an error be tied to a release, to decide on a rollback. `unknown` locally. |
| `deployment.environment` | `development` \| `homolog` \| `production` | Used by SigNoz's environment filters (Services, Logs). |
| `deployment.environment.name` | the same value | The current OpenTelemetry semantic convention. Send both. |

The environment comes from explicit configuration (`Observability:Environment` on the backend,
`observability.environment` on the frontend). The host's own environment name is only a fallback,
normalized to the three canonical values; an unrecognized name is sent as-is (so it shows up in SigNoz
and can be fixed), never guessed.

## 2. Error contract

- The backend returns the Trace ID (32 hex chars, W3C format) on **every** error response, through two
  channels: an `X-Trace-Id` header (every response) and a `traceId` field in the body
  (ProblemDetails/a custom envelope, or that framework's equivalent).
- The frontend **shows** the Trace ID + a copy button + support guidance **only** for a system failure:
  status `0` (network) or any status outside `400, 401, 403, 404, 422, 429`.
- The message shown to the user never exposes internal structure (a table/column/procedure name, a
  stack trace).
- Details: `error-contract.md`.

## 3. Context propagation

- `traceparent`/`tracestate` only go to this project's **own API and Auth server** (an explicit list
  on the frontend). Never to a third-party domain (Microsoft login/Graph, payment gateways, CDNs):
  besides leaking context, the extra header triggers a CORS preflight the third party refuses —
  **this can break login**.
- Between backend services, propagation is automatic through an instrumented HTTP client; a client
  built inline per call, outside the framework's pooled-client mechanism, stays instrumented but is
  its own technical debt (e.g. socket exhaustion in .NET) — report it.
- Queues and jobs: explicit propagation through the message's own headers (`messaging-workers.md`).

## 4. Secrets

- The ingestion key is **never** committed to a versioned file. Local: the language's own local-secret
  mechanism (`dotnet user-secrets`, a `.env` kept out of git, etc.). Deploy: a secrets manager (Azure
  Key Vault by default) or an environment variable injected by the App Service/pipeline.
- Frontend: a browser ingestion key is public by nature (it only writes). Even so: a placeholder in the
  repo, the real value injected by the pipeline, **a separate key per frontend and per environment**
  (revocable without touching the backend).
- With no endpoint or key, the application **starts up normally** and simply doesn't export.
  Observability must never take an application down.

## 5. Data privacy and client data

- `enduser.id` only as a stable, opaque identifier (`sub`, `oid`, an internal GUID). Never an email,
  a national ID, a name, or a phone number as a span/log attribute.
- URLs with PII in the path/query (e.g. `/customers/123-45-6789`) end up on the span. Report the
  affected routes.
- Exception messages can carry data values (e.g. a duplicate-key violation that includes the value).
  They go to SigNoz — treat the SigNoz account as a personal-data processor (a data-processing
  agreement, minimal retention).
- **Never mix clients** in the same SigNoz account without an explicit decision. A shared account is a
  flag to raise.
- SigNoz Cloud has data centers in the US, the EU, and India — **there is no Brazil region**. For a
  client in a regulated sector, confirm this with the client (contract/DPO/cloud policy) before going
  live in production; alternatives: a self-hosted SigNoz, or one managed by SigNoz inside the client's
  own cloud.

## 6. Cost and volume

- SigNoz's cost is proportional to the volume ingested. Levers, in this order:
  1. Filter health checks, Swagger/OpenAPI UI, and static assets out of traces.
  2. The minimum log level exported (`Information` in production; never `Debug`).
  3. Turn off click-instrumentation on the frontend if nobody uses it.
  4. Sampling — last. Head-based sampling decides before knowing whether a request will fail: below
     100%, part of the Trace IDs shown to users **won't have a complete trace** in SigNoz (the error
     log still goes through, with the same `traceId`). If you need to cut volume a lot, the right path
     is tail sampling in an OpenTelemetry Collector, not lowering the SDK's own ratio.

## 7. A project that already has something — inherit, don't replace

| Found | Action |
|---|---|
| OpenTelemetry already exporting to another backend (Jaeger, Tempo, App Insights, Datadog, Elastic) | Don't switch exporters without an explicit decision. Only add what's likely missing: resource attributes (§1), the error contract (§2), propagation (§3). |
| A classic Application Insights SDK | `Activity.Current` (or that platform's equivalent) works the same — the error contract doesn't depend on migrating. Migrate to OTLP only if the project is adopting SigNoz. |
| Structured logging (Serilog/NLog/a JSON logger) with no tracing | Keep the current sink; add OpenTelemetry on top; enrich the logger with the current trace/span ID. |
| A global error handler with no Trace ID | Don't rewrite it — add the field, preserving the existing exception → status mapping. |
| An existing correlation field (`correlationId`, `requestId`) | Ask: keep the existing name, or standardize on `traceId`? Never two names for the same thing. |
| Nothing of the above | Apply everything from scratch. |

## 8. Delivery governance

- Branch `feature/<TICKET>-observability-otel` off `main`; PR → `develop` (staging/homolog) before
  → `main` — or whatever branching convention the target repository already follows; `setup` asks
  rather than assumes.
- Build and tests green before handing off. Push/PR only with explicit confirmation.
- Every AI-produced output is reviewed by a person before merging.
